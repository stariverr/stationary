# 所有权、共享与团队

本文确定资源由谁拥有、如何共享，以及以后团队如何接入。对会产生费用或持有凭据的资源（例如 AI 供应商）尤其关键。

## 1. 所有权与访问权

这是两个不同的问题：

- **所有权**：谁持有资源、为它付费、管理它的凭据，并在人员变动时保有它。
- **访问权**：谁可以使用别人拥有的资源。

所有权是资源上的单个字段。访问权通过独立的表授予（`LibraryUserAccess`、`LibraryGroupAccess`，见 [system_design.zh-Hans.md §5](system_design.zh-Hans.md)）。两者从不混用：授予访问权永远不会转移所有权。

## 2. 当前模型

- 用户拥有媒体库（`library.owner_id`）。
- 账户级资源由**拥有媒体库的同一主体**持有，目前就是用户本人。
- AI 供应商（`ai_provider.owner_id`）及其模型归该所有者，被其名下所有媒体库共用。
- 媒体库只记录各角色使用哪个模型（`library.ai_bindings`）。

### 规则：凭据跟随媒体库所有者

媒体库只能绑定**与自己所有者相同**的供应商下的模型。`resolveBindingConfig` 每次解析都会校验这一点：违反规则的绑定在保存时会被拒绝，在运行时会被忽略。

由此得到：

- 任何有权在库内处理媒体的人（例如 `EDITOR` 协作者）使用的都是所有者的供应商，费用由所有者承担。这是有意为之：是所有者决定为这个库开启 AI。
- 只有所有者可以增删改供应商和模型，或修改媒体库的模型绑定。
- 账户级接口拒绝媒体库范围的 API Token。

## 3. 凭据

- API Key 使用 `SECRETS_ENCRYPTION_KEY`（32 字节，base64）以 AES-256-GCM 加密存储，密文带版本前缀（`v1:`）。
- 明文 Key 永远不离开服务端，接口只返回提示（`••••abcd`）。编辑供应商时不填写新 Key 即保留原有 Key。
- 共用同一数据库的所有环境必须使用相同的 `SECRETS_ENCRYPTION_KEY`。更换后已存储的 Key 将无法解密，需要重新填写。
- 供应商地址由用户填写、由服务端请求，默认不做限制（自托管的 Ollama、vLLM 和局域网网关可直接使用）。当不受信任的用户可以添加供应商时，把 `AI_BLOCKED_CIDRS` 设为逗号分隔的 IPv4/IPv6 CIDR 列表，例如 `169.254.0.0/16,fe80::/10` 以屏蔽云厂商 metadata 地址。设置后，保存供应商时和每次请求前都会解析并检查地址，并拒绝重定向。供应商返回的错误只回显 JSON 响应体。

## 4. 团队（规划）

团队将**拥有**媒体库，采用 GitHub Org、Vercel Team、Linear Workspace 使用的账户模型：

- 每个用户有一个个人账户；团队也是一个账户。
- 媒体库、AI 供应商以及以后的计费/额度都归属于账户（`account_id`）。
- 成员通过角色操作团队资源：团队管理员管理供应商与凭据，成员使用它们。
- 共享表继续保留，用于向账户以外的人授予访问权。

只靠共享无法支撑团队，因为它回答不了：

1. **成员离开怎么办。** 如果库归某个人所有，库、供应商和 Key 都会随这个人一起离开。
2. **谁来付费。** AI 处理是持续的成本，需要一个可以统计用量和额度的归属主体，而不是碰巧拥有这个库的某位成员。
3. **谁来管理。** 轮换 Key、更换模型、删除媒体库都需要"团队管理员"角色，共享模型表达不了。

### 在那之前保持不变的约定

- 团队落地前不提前建账户抽象。所有权保持为 `owner_id`，在每张有归属的表上含义相同。
- 引入团队时，`library.owner_id` 与 `ai_provider.owner_id` 一起替换为 `account_id`（已有数据指向所有者的个人账户）。因为两者遵循同一条规则，这是一次机械性迁移。
- 团队的媒体库永远不能使用个人供应商。个人 Key 会在成员离开时失效，管理员也无法轮换。
- 媒体库转移到另一个账户时，需要从新所有者的供应商中重新选择模型。只要新供应商提供同一模型，已有向量依然有效，因为向量空间 ID 不包含供应商（见 [ai_hybrid_search.zh-Hans.md §2.1](ai_hybrid_search.zh-Hans.md)）。
