# Multi-Space Hybrid Search MVP

> [简体中文](./ai_hybrid_search.zh-Hans.md)

This document records the planned MVP architecture for AI-enriched search in Stationary. It is a design and implementation guide; some components may be introduced incrementally.

---

## 1. Goals

Stationary stores posts and media assets from multiple platforms. Search must support both precise textual retrieval and visual discovery:

- Exact or fuzzy keyword search over titles, descriptions, tags, authors, OCR, and AI-generated captions.
- Text semantic search over composed post/media documents.
- Visual or multimodal semantic search over image content, color, layout, style, and mood.
- Strict Library-level access control before retrieval and rank fusion.
- Mathematically safe handling of embeddings from different models and pipelines.

The MVP uses three complementary retrieval signals:

```text
keyword match
+ text semantic vector search
+ visual/multimodal vector search
→ Reciprocal Rank Fusion (RRF)
→ deduplicated entity results
```

---

## 2. Core Principles

### 2.1 Embedding Space Segregation

Vectors generated by different embedding models, model versions, task types, dimensions, preprocessing rules, or normalization policies belong to different semantic spaces. Cosine or distance comparisons across different spaces are invalid even if the physical vector dimensions match.

Therefore every embedding row carries an `embedding_space_id`, computed from the model definition as `{modelName}:{dimension}:{taskPrefixType|plain}`, for example:

```text
gemini-embedding-2:768:gemini-asymmetric
qwen3-vl-embedding:1024:plain
```

The space ID deliberately excludes the provider connection: the same model served by another provider produces comparable vectors, so moving it does not require re-embedding. Anything that changes the vectors (model, output dimension, input template) changes the ID.

### 2.2 Canonical Lifecycle Integration

AI-derived records mirror existing lifecycle fields:

- `delete_status`
- `delete_time`
- `recycle_time` where applicable

However, search correctness must still be evaluated against canonical `Post` and `Media` records. A search result is valid only when the canonical entity satisfies:

```sql
delete_status = 'ACTIVE'
AND recycle_time IS NULL
```

AI tables may keep denormalized lifecycle fields for indexing and operational cleanup, but they must not become the sole source of truth for visibility.

### 2.3 Pre-Filter Security Bounds

All retrieval paths must enforce Library access boundaries before expensive or ranking-sensitive operations:

1. Resolve the set of libraries visible to the current user.
2. Apply that boundary in keyword search, text semantic search, and visual semantic search.
3. Join canonical `Post` / `Media` rows and re-check `library_id`, `delete_status`, and `recycle_time`.
4. Only then perform rank fusion and return results.

RRF must never be used to merge unauthorized candidates and filter them afterward.

## 3. Input Sources vs. AI Calls

The search enrichment pipeline uses only two kinds of source inputs:

1. Raw image bytes.
2. Composed descriptive text.

To extract maximal value from those sources, the MVP performs three categories of AI calls:

| Channel                       | Input         | Model family               | Output                                             | Purpose                                                                                     |
| :---------------------------- | :------------ | :------------------------- | :------------------------------------------------- | :------------------------------------------------------------------------------------------ |
| Image Understanding           | Image bytes   | Gemini Flash               | Caption, tags, objects, colors, styles, scene, OCR | Convert visual content into structured human-readable metadata.                             |
| Visual / Multimodal Embedding | Image bytes   | `multimodal-embedding-004` | 1408-dimensional vector                            | Search by visual similarity, mood, color, composition, and cross-modal visual descriptions. |
| Text Semantic Embedding       | Composed text | `text-embedding-004`       | 768-dimensional vector                             | Search over post text, AI captions, OCR, tags, authors, concepts, and named entities.       |

This distinction is important:

- The system has two source modalities: image and text.
- It has three AI-derived retrieval/enrichment signals: VLM metadata, visual embeddings, and text embeddings.

### Example

A Xiaohongshu post contains:

- Image: a latte with heart-shaped latte art on a warm wooden table.
- Text: “I found a very healing coffee near the Seine, highly recommend this Left Bank cafe.”

Search behavior:

- Query `Seine` or `Left Bank cafe`: keyword and text semantic channels should dominate because the terms are textual concepts or named entities.
- Query `warm Japanese-style coffee material`: visual/multimodal search should contribute strongly because the request describes mood, color, and composition.
- Query `coffee latte art`: all three channels may contribute.

Note: multimodal embedding spaces can accept text queries and image documents in the same space. They are not “pixel-only” models. Their strength is mapping visual-language descriptions to image content. They should not replace keyword or text semantic retrieval for exact entities, source text, author names, or business metadata.

## 4. Planned Data Model

The MVP introduces the following logical tables in `apps/server/src/db/schema/index.ts`.

### 4.1 `library_embedding_space`

Records which spaces a library writes, per embedding role (`textEmbedding` / `imageEmbedding`).

- `status = ACTIVE`: the space search reads; one per role.
- `status = BUILDING`: a new space being filled after a model change. It replaces the ACTIVE space once its backfill task has finished, its queue has drained, and both of these hold:
  - failed vectors are at most 5% of the finished ones;
  - it holds at least 95% as many READY vectors as the ACTIVE space.

  Otherwise it stays BUILDING and `/api/ai/status` reports `blocked` (`too_many_failures` / `low_coverage`). "Retry failed" in settings requeues failed vectors and, when coverage is short, starts a new backfill.
- `status = RETIRED`: the replaced ACTIVE space. Its vectors are kept for 7 days, neither searched nor written. Choosing its model again in that time turns it back into a BUILDING space that only catches up on what changed, without re-embedding everything. The embedding worker drops it once it expires. Each role has at most one RETIRED space.
- `model_id`: the model producing the space. Serving the same space from another provider only updates this column; nothing is rebuilt.
- `backfill_task_id`: the AI task that re-processes the whole library (media discovered page by page).

During a switch, enrichment writes both ACTIVE and BUILDING spaces while search reads only ACTIVE, so search never goes dark.

### 4.2 `asset_search_document`

A denormalized search document for posts and media.

It holds what search reads and nothing else:

- `title`: the media title, else the post title
- `content`: media and post titles and descriptions, post and media tags with their aliases, and the AI scene, caption and OCR text when available
- `source` and `media_type`: filter columns
- `content_hash`: decides whether the document and its text embeddings are rewritten

`content` holds plain field values, one per line, without field labels: a label such as `Title:` would make every document match the word "title". The document is written for every indexed media item whether or not the library has AI configured, and a failed image description never withholds it; it carries the best stored description and is rewritten when a new one lands.

Recommended uniqueness:

```text
(entity_type, entity_id)
```

### 4.3 `asset_ai_metadata`

Structured AI analysis results for an asset. It is the source of truth for AI-generated content: search copies parts of it into the search document, and the media detail API returns the selected result as `ai` for display.

Typical fields:

- caption
- tags
- objects
- colors
- styles
- scene
- OCR text
- model
- metadata pipeline ID
- processing status
- last error

The metadata pipeline is versioned independently from the model name: it is the prompt version plus the output language, for example:

```text
image-metadata:v2:zh-Hans
```

The `model` column records which model wrote a description. Switching the describe model therefore leaves existing descriptions in place and only new or changed content uses the new model, unless the user asks to re-describe the library (a library-wide run with `redescribe`, which describes again every item whose description was written by another model).

Recommended uniqueness:

```text
(entity_type, entity_id, metadata_pipeline_id)
```

Search documents and result explanations use the current pipeline's result, otherwise the newest result of an earlier pipeline, so a language change keeps descriptions searchable while the library is re-described. Once the current pipeline stores a result for a media item, that item's older pipeline rows are deleted.

### 4.4 `asset_embedding`

Both the vector table and the embedding request queue: a row is queued as `PENDING` and becomes `READY` once the embedding worker stores its vector.

Key fields:

- `entity_type`, `entity_id`, `library_id` (pre-filter), `document_id`.
- `embedding_space_id`, `embedding_role` (`AI_CAPTION`, `IMAGE_PRIMARY`, ...), `input_modality`, `dimension`.
- `embedding`: dimensionless `halfvec`, null while queued.
- `content_hash`: hash of this row's own input (source file hash for images, the embedded text for text roles).
- `source_file_id`: image input; `input_text` / `input_title`: text input, cleared once the vector is stored.
- `embedding_status`: `PENDING`, `READY`, `STALE` (superseded by a newer input in the same space and role), `FAILED` (given up after repeated errors; can be retried on demand).
- Queue fields: `available_at` (claimable from; pushed forward as a lease when claimed), `attempt_count`, `last_error`.

Unique key:

```text
(entity_type, entity_id, embedding_space_id, embedding_role, content_hash)
```

### 4.5 Embedding Queue

- Enrichment only describes images and writes search documents; it queues a row for every space being written. Until the new row completes, the previous `READY` vector keeps serving search.
- The embedding worker (2 loops per instance) claims batches of one library, space and modality. Batch size depends on the provider (texts: up to 64, DashScope 20; images: Gemini 6, others 1).
- Rows that failed before are retried alone so one bad input cannot fail a whole batch; throttled batches are deferred without counting an attempt.
- Enqueuing publishes a Redis wake-up to every instance; a 10-second poll covers missed wake-ups.
- Work for recycled media waits until the media is restored and neither blocks promotion nor counts in progress. Deleting media for good removes its vectors, search document and image metadata in the same transaction.
- Text inputs are cut to about 90% of the model's `maxInputTokens` using a conservative estimate (CJK 1.5 tokens per character, otherwise 1 per 3 characters); documents list titles and tags before OCR text, so the tail is dropped first.

## 5. Vector Storage and Indexing

### 5.1 Generic Vector Column

Use a single half-precision pgvector column without a fixed dimension:

```sql
embedding halfvec NOT NULL,
CONSTRAINT asset_emb_dimension_check CHECK (vector_dims(embedding) = dimension)
```

Provider adapters validate the returned length against the model definition before insert; the constraint is the last line of defense. `halfvec` halves storage and raises the HNSW limit from 2000 to 4000 dimensions.

### 5.2 Partial HNSW Indexes

HNSW needs a fixed dimension, so the schema declares one partial expression index per supported dimension (`EMBEDDING_DIMENSIONS` in `features/ai/model-schema.ts`: 256, 384, 512, 768, 1024, 1536, 2048, 2560, 3072). Model definitions may only use these dimensions; larger native outputs are shortened through MRL.

```sql
CREATE INDEX asset_emb_hnsw_1024 ON asset_embedding
USING hnsw ((embedding::halfvec(1024)) halfvec_cosine_ops)
WHERE dimension = 1024;
```

Queries cast with the same literal dimension, filter `dimension = <literal>`, order by distance with `LIMIT`, and apply distance cut-offs afterwards. Space, role and library filters run during the scan with `hnsw.iterative_scan = relaxed_order` (pgvector ≥ 0.8).

### 5.3 Extensions and Migration Notes

Required PostgreSQL extensions:

```sql
CREATE EXTENSION IF NOT EXISTS vector;
CREATE EXTENSION IF NOT EXISTS pg_trgm;
```

Operational notes:

- `CREATE INDEX CONCURRENTLY` must run outside transaction blocks.
- Extension initialization should be handled as a dedicated bootstrap step because managed databases may require elevated permissions or extension allow-listing.
- Development can use normal `CREATE INDEX`; production should prefer `CREATE INDEX CONCURRENTLY` for large tables.
- Drizzle-generated DDL may need manual companion migrations for extensions, pgvector HNSW indexes, and trigram indexes.

### 5.4 Keyword Indexes

`asset_search_document` stores its folded title and content as generated columns (folding rules in 5.5), and the trigram indexes are built on them:

```sql
ALTER TABLE asset_search_document
  ADD COLUMN folded_title text GENERATED ALWAYS AS (replace(lower(normalize(title, NFKC)), 'ß', 'ss')) STORED,
  ADD COLUMN folded_content text GENERATED ALWAYS AS (replace(lower(normalize(content, NFKC)), 'ß', 'ss')) STORED;

CREATE INDEX search_doc_folded_title_trgm_idx ON asset_search_document USING gin (folded_title gin_trgm_ops);
CREATE INDEX search_doc_folded_content_trgm_idx ON asset_search_document USING gin (folded_content gin_trgm_ops);
CREATE INDEX search_doc_library_idx ON asset_search_document (library_id);
```

The folding expression is defined once in code (`searchFold`) and used for both the generated columns and the query patterns. Queries filter on both `asset_search_document.library_id` and `media.library_id`: the first limits the scan to the library, the second remains the authority for access.

Why stored columns rather than expression indexes: when a term is common or only two characters long, the query scans the whole library and computes sort keys for every match, and with expression indexes every row re-runs `normalize()`. Measured on a single library of 200k documents, the worst case dropped from 1.3–2.4 s to 0.13–0.26 s; selective terms that use the index stay under 10 ms. The cost is roughly double the text storage.

### 5.5 Keyword Search (Multilingual)

Supported languages today: Chinese, Japanese, English, German.

The keyword channel is for **exact recall**: names, brands, identifiers, proper nouns, and mixed CJK/Latin text that vectors tend to miss. Synonyms, full natural-language sentences, and cross-language search belong to the semantic channels, so the text embedding model should be multilingual.

**Principle: store the original text, segment only the query, match substrings.** Every segment is a substring of the query, so a segmentation mistake only widens the match and never recalls less than matching the whole query. Documents are never tokenized, so there is no index-side dictionary to maintain and changing the segmenter never requires rebuilding data.

1. **Folding** (a database expression shared by documents and queries): NFKC unifies full-width and half-width forms (`ＩＰＨＯＮＥ１５` → `iphone15`, `ｶﾀｶﾅ` → `カタカナ`), then lowercase, then `ß` → `ss`. Diacritics are kept so `Bar` does not match `Bär`. `title` and `content` keep the original text, which embeddings and reranking use; the folded copies live in generated columns.
2. **Query segmentation**: split on whitespace first; English and German stop here. Segments containing Han or kana go through `Intl.Segmenter` (the runtime's ICU), then:
   - adjacent single Han characters are joined back, restoring words missing from ICU's dictionary (ICU splits `赛博朋克` into single characters);
   - lone hiragana characters (particles such as `の`, `は`, `が`) are dropped.

   Every segment must appear as a substring of the title or the content. Full natural-language sentences may therefore miss here and are left to the semantic channels.
3. **Ranking** (so RRF ranks carry meaning):
   1. the title contains the whole query;
   2. number of whole-word matches (`\m…\M` word boundaries: `art` ranks above `start`, `Tür` above `Haustür`; Chinese and Japanese have no word boundaries, so this has no effect there);
   3. number of terms matched in the title;
   4. the content contains the whole query;
   5. creation time.

Known limitations:

- Terms shorter than three characters (most two-character Chinese words) cannot use trigram indexes and fall back to a sequential scan within one library.
- Hiragana and katakana are not interchangeable; diacritics of other Latin languages and scripts such as Thai are not handled yet.

Upgrade path (only when a trigger is hit; the architecture stays the same):

| Trigger | Upgrade |
|---|---|
| Two-character queries become noticeably slow | Add `pg_bigm` |
| More queries that ICU plus the joining rule handles poorly | In the segmentation function, use jieba for Chinese and Lindera / kuromoji for Japanese (surface forms only, no lemmatization) |
| Documents get long (OCR, transcripts, PDF text) and the Postgres image is under our control | ParadeDB `pg_search` (BM25) |
| Product requires search-as-you-type and typo tolerance | Meilisearch for the keyword channel only; Postgres stays the single source of truth |

Rejected: `tsvector` (needs a per-document language configuration; the default parser does not segment Chinese), sparse vectors such as SPLADE (the keyword channel would depend on AI configuration), Elasticsearch / Typesense (too costly to operate for self-hosting).
```

Also maintain B-tree indexes for filtering:

```sql
CREATE INDEX IF NOT EXISTS asset_search_doc_library_status_idx
ON asset_search_document (library_id, delete_status, entity_type, entity_id);

CREATE INDEX IF NOT EXISTS asset_embedding_space_library_idx
ON asset_embedding (embedding_space_id, library_id);

CREATE INDEX IF NOT EXISTS asset_embedding_entity_idx
ON asset_embedding (entity_type, entity_id);
```

## 6. Provider Abstraction

The AI provider should explicitly model query/document purpose for text embeddings:

```ts
export interface ImageAiMetadata {
    caption: string;
    tags: string[];
    objects: string[];
    colors: string[];
    styles: string[];
    scene: string;
    ocrText: string;
}

export interface EmbedTextParams {
    text: string;
    spaceId: string;
    purpose: "QUERY" | "DOCUMENT";
}

export interface EmbedImageParams {
    imageBuffer: Buffer;
    mimeType: string;
    spaceId: string;
}

export interface AiProvider {
    embedText(params: EmbedTextParams): Promise<number[]>;
    embedImage(params: EmbedImageParams): Promise<number[]>;
    describeImage(imageBuffer: Buffer, mimeType: string): Promise<ImageAiMetadata>;
}
```

Implementation requirements:

- Route by `spaceId` and reject unknown spaces.
- Use task types from `embedding_space.config`.
- Validate output dimension immediately.
- Keep API keys in environment variables only.
- Use schema validation for structured image metadata responses.
- Make generation idempotent using `content_hash` and pipeline IDs.
- Tests should mock providers rather than calling external AI APIs by default.

## 7. Search Flow

A high-level MVP search flow:

```ts
async function search(params: SearchParams, userId: string) {
    if (!(await canSearchLibrary(userId, params.library_id))) {
        return { list: [], total: 0 };
    }

    const textSpace = "gemini:text-embedding-004:768:cosine:v1";
    const visualSpace = "gemini:multimodal-embedding-004:1408:cosine:v1";

    const [keywordResults, textSemanticResults, visualSemanticResults] = await Promise.all([
        keywordSearch(params, params.library_id),
        params.q ? textSemanticSearch(params.q, textSpace, params.library_id) : [],
        params.q ? visualSemanticSearch(params.q, visualSpace, params.library_id) : [],
    ]);

    return reciprocalRankFusion([keywordResults, textSemanticResults, visualSemanticResults], {
        k: 60,
        weights: [1.0, 1.0, 1.2],
        dedupeKey: (item) => `${item.entity_type}:${item.entity_id}`,
    });
}
```

Important details:

- Keyword search should be strongest for exact names, source text, author names, brands, and platform-specific identifiers. The query is folded and segmented, and every segment must match the title or content as a literal substring (`%` and `_` escaped); ranking is described in 5.5.
- Text semantic search should cover paraphrases and conceptual matches over composed documents.
- Visual/multimodal search should cover style, mood, color, composition, and visual-language descriptions.
- Vector channels should retrieve more candidates than the final page size before RRF.
- `total` in hybrid search is not necessarily an exact database-wide total; prefer documenting it as candidate count or returning `hasMore` if precise pagination is not implemented.
- Query vectors are cached per embedding space and query text for 10 minutes: roles sharing one model embed a query once, and paging reuses it.
- Each semantic channel drops matches beyond the embedding model's `matchDistance` (`text` for text-to-text, `image` for text-to-image; defaults 0.5 and 0.6). The cut-offs are editable on the model without re-embedding.
- When a library binds a rerank model, the top 50 fused candidates are reordered by the reranker against their search document text (Cohere-style `/rerank`); the rest keep their fused order, and a failing reranker leaves the fused order. Scores are cached so paging reranks once, and results expose them as `matched_details.rerank`.
- When an AI channel should have taken part but did not (its bound model cannot be resolved, the call failed or was throttled), search still returns the other channels' results and lists `{ channel, reason }` in `degraded`. `channel` is `text_semantic`, `visual_semantic` or `rerank`, or `ai` when the library's AI configuration cannot be loaded at all; `reason` is the error kind (e.g. `CONFIGURATION`, `AUTHENTICATION`, `THROTTLED`). The web app shows a "results may be incomplete" notice above the results.
- Results carry structured `matched_details`; clients render the explanation in the viewer's language.
- Image descriptions are written in the library's `ai_language` (OCR keeps the original text). The language is part of the metadata pipeline id, so changing it re-describes the library.

## 8. Lifecycle and Sync Rules

When deleting a `Post` or `Media`, update AI-derived tables in the same transaction where practical:

```text
asset_search_document.delete_status = 'DELETED'
asset_ai_metadata.delete_status = 'DELETED'
asset_embedding.delete_status = 'DELETED'
```

Also set `delete_time`.

For recycle/restore and library movement:

- Search must rely on canonical joins to `Post` / `Media` for final visibility.
- Derived `library_id` fields should be synchronized when entities move libraries.
- Stale derived rows must not cause access leaks because canonical `library_id` and lifecycle checks are always reapplied.

## 9. Verification Checklist

Automated checks:

- Schema migrations create required tables and constraints.
- pgvector dimension mismatch fails fast.
- Provider output dimension validation throws before database insertion.
- Unknown `embedding_space_id` is rejected.
- RRF deduplicates by `entity_type:entity_id`.
- Library access filtering applies to keyword, text semantic, and visual semantic paths.
- Recycled or deleted `Post` / `Media` rows do not appear in search.

Manual checks:

1. Seed `embedding_space` rows for active text and multimodal spaces.
2. Process representative images such as coffee photos, dark technology graphics, screenshots with OCR text, and multi-image posts.
3. Verify generated metadata, text embeddings, and image embeddings have expected dimensions.
4. Run natural language searches across restricted libraries and verify no unauthorized results appear.
5. Inspect matched channels and rankings for keyword-heavy, concept-heavy, and visual-style-heavy queries.

## 10. MVP Non-Goals

The first implementation does not need to solve every future retrieval problem. The following can be deferred:

- Full video understanding beyond selected keyframes.
- Audio embeddings.
- Cross-model migration tooling.
- Exact global result counts for hybrid search.
- Sophisticated learning-to-rank models.
- Automated quality evaluation dashboards.

The MVP should prioritize correctness, safe access boundaries, idempotent AI processing, and clear separation of embedding spaces.
