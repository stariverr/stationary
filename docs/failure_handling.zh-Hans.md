# 下载失败处理方案

状态：提案（2026-11-19），还没有实施。实施后要回头修改 [job_queue.zh-Hans.md](./job_queue.zh-Hans.md) 和 [media_refactor.zh-Hans.md](./media_refactor.zh-Hans.md) 的相关章节（第 12 节），因为那两份文档按"现在是什么样"来写。

范围：`download` 流水线的失败怎么分类、怎么记录、怎么显示、怎么修，以及为了让用户的修复不被下一次同步撤销，导入要遵守哪些规则。`avatar` 只定规则，代码以后再改（第 10 节）。预览图、AI 这些衍生流水线的失败模型不变。

怎么读：

- 想了解为什么这样设计：读第 1、2、3 节。
- 实施后端：读第 4 到 8 节。
- 实施界面：读第 9 节。
- 上线：读第 11、12 节。

## 1. 现状和问题

2026-11-18 线上约有 52 个下载失败：

| 类别 | 数量 | 原因 |
|---|---|---|
| 签名过期 | 约 20 | 抖音、小红书的签名 URL 过期，返回 403 |
| 内容和类型不符 | 约 33 | 24 个抖音 LIVE_PHOTO 的"视频"其实是背景音乐（mp3 / m4a）；7 + 2 个小红书 VIDEO 的"视频"是只有音频的流（`…_338.mp4`）。这些是一次性迁移后才暴露出来的 |

现在的处理方式有这些问题：

- **403 白白重试。** 只有 400、404、410 算"输入被拒"（`DownloadStatusError.rejected`），403 会退避重试 5 次，但签名过期的地址重试永远不会成功。
- **"重试"用的还是旧地址。** 媒体卡片上的"重试同步"（`retry-sync.ts`）和任务页上的"重试失败"（`status.ts` 的 `retryFailures`），都拿同一个 URL 再试。服务端没法让采集端重新抓取。
- **坏内容会被记成 COMPLETED。** 导入只检查原件的数量（`originalCountError`），类型和组合要等下载探测完才检查（`getMediaCompletionError`）。所以单个原件只要能被探测，就记为 `COMPLETED`，然后整个媒体报一条含糊的组合错误。`COMPLETED` 的原件永远不会重新下载，这 33 个就一直卡在这里。
- **错误只有自由文本。** `last_error` 没有原因码，界面只能原样显示，也给不出对应的修复方式。
- **用户修不了，或者修了会被撤销。**
  - `deleteOriginal` 拒绝会破坏组合的删除，也不能改媒体类型。所以一个 LIVE_PHOTO 有一张正常的图加一个坏的"视频"时，只能整个删掉。
  - 用户替换或删除的导入原件，下次同步会被加回来。
  - 再次导入会覆盖用户改过的类型、标题和描述。
  - 用户上传的封面会被导入的封面覆盖（`CoverService.syncImported`）。
- **界面只有原始错误和"全部重试"。** 任务页的失败列表（`PipelineInspector.vue`）显示原始文本，没有链接，只有一个"全部重试"按钮。

## 2. 原则

1. **下载是 reconcile。** 它让"媒体声明的每个来源都有文件"这个状态收敛，属于一次性落地的那一种（第 3 节）。
2. **失败和输入绑定。** 失败只对当时用的那个 URL 成立。URL 一变，失败就作废，系统自动再下载一次。
3. **坏内容不入库。** 内容和声明不符的文件，不能作为已完成的原件写进去。
4. **一份事实，多个视图。** 失败的事实只存在来源行上。媒体和帖子的状态是从来源行汇总出来的摘要，各个界面只是从不同角度显示它。
5. **能让用户修的就让用户修，同步不撤销用户的修改。**
6. **只在可能有用的地方放"重试"按钮。**

## 3. 下载在任务模型里的位置

[job_queue.zh-Hans.md](./job_queue.zh-Hans.md) 第 1 节把后台工作分成 reconcile 和 operation 两类。分界只看一条：工作是由**状态**驱动，还是由**命令**驱动。下载是状态驱动的：

| 检验 | 下载的实际情况 |
|---|---|
| 同一个导入发两次，会做两次工作吗？ | 不会，`source_key` 相同就不重新下载 |
| 采集端不再提供某个来源 | 删掉对应的文件（双向差异） |
| 用户关心什么 | 这个媒体有没有文件，没有的话为什么；不关心"第 N 次导入"的进度 |
| 怎么取消 | 删帖子或删媒体，也就是改数据 |
| 失败之后输入变了 | 自动再试一次 |

所以 reconcile 的定义要从"衍生数据"放宽成"让状态收敛到期望"，下面分两种。这不是新增的任务类型：

| 种类 | 流水线 | 什么时候算收敛 | 失败什么时候作废 |
|---|---|---|---|
| 持续衍生 | `preview`、`ai.describe`、`ai.index`、`ai.text`、`ai.image` | 产出和当前的源数据、配置一致；源数据或配置一变就重算 | 源数据或配置的哈希变化 |
| 一次性落地 | `download`、`avatar` | 稳定键对应的合法文件已经落地；落地之后，后续的 URL 刷新一律忽略 | URL 变化，或者稳定键变化 |

一次性落地这一种有两个特点：输入来自外部而且会过期，所以"输入被拒"很常见；产出是源数据，不能重新算，用户也会直接编辑它。这两点都由失败模型（第 4 节）和所有权规则（第 8 节）处理，不需要改执行方式。

以后如果要做"导入记录"（哪个时间推了哪些帖子，哪些在入库前就被拒了），它是在下载之上另加的一层：只记录"发生了什么"，不接管下载，也不另存一份来源的状态。

## 4. 来源行的状态

适用于 `media_original`、`media_caption`、`media_cover` 三张表。`media_lyrics` 现在没有导入来源，不涉及。

### 4.1 列

| 列 | 含义 |
|---|---|
| `status` | `PENDING`、`IN_PROGRESS`、`COMPLETED`、`FAILED`，保留为普通的可写列，方便直接查看、筛选和汇总 |
| `last_error` | 当前 URL 上最近一次的错误，给人看的详细信息 |
| `error_kind` | 错误类别（第 5 节），新增 |
| `error_source_url` | 出错时用的 URL，新增 |

错误三列（`last_error`、`error_kind`、`error_source_url`）表示**当前 URL 上最近一次的错误**。`status` 说明这个错误是终态（`FAILED`），还是还会重试（`PENDING`、`IN_PROGRESS`）。

### 4.2 约束

字幕表的文件列是 `vtt_file_id`，下面统一写成"文件列"：

- `COMPLETED` ⇔ 文件列有值；`COMPLETED` ⇒ 错误三列都为空。现有的 `*_file_when_completed` 约束补上后半句。
- `FAILED` ⇒ 错误三列都有值。
- 错误三列要么都为空，要么都有值。
- 有错误 ⇒ `error_source_url = source_url`。

最后一条同时管两件事：错误永远对应当前的 URL；导入换了 URL 时必须清掉旧错误，忘了清，数据库会直接拒绝。用户上传的行没有 `source_url`，永远是 `COMPLETED`，也不会有错误。

`PENDING` 和 `IN_PROGRESS` 可以带着上一次尝试的错误：download 一次重试周期可能很长（单次运行最长 2 小时，最多 5 次，中间还有退避），这段时间里能看到"重试中：超时"，比只显示一个 `PENDING` 有用。

### 4.3 谁在什么时候写

| 时机 | 写什么 |
|---|---|
| 导入了新的键 | 插入一行 `PENDING`，没有错误 |
| 导入了已有的键，URL 变了，这一行还没 `COMPLETED` | 更新 `source_url`，改成 `PENDING`，清空错误 |
| 导入了已有的键，这一行已经 `COMPLETED` | 只更新 `source_url`，不重新下载 |
| 一次运行开始下载这个来源 | `IN_PROGRESS`（原件、字幕、封面都写） |
| 遇到可以重试的错误 | `PENDING` 加上错误三列，交给队列退避重试 |
| 遇到要拒绝的错误 | `FAILED` 加上错误三列 |
| 重试次数用完（`recordFailure`） | 仍在 `PENDING` 或 `IN_PROGRESS` 的行改成 `FAILED`；`last_error` 和 `error_kind` 保留这一行自己记过的值，没有记过的才用运行级的错误补上（`INTERNAL`）；`error_source_url = source_url` |
| 下载、探测、校验都通过 | `COMPLETED`，写入文件列，清空错误 |
| 用户点"重试" | `PENDING`，清空错误，`markChanged(media.source)` |

所有写失败的语句都带上条件 `source_url = 这次用的 URL`。运行期间导入换了新 URL 的话，旧 URL 上的失败直接作废，不会写进去，也不会触发约束错误。新 URL 已经让这个媒体重新入队了。

### 4.4 媒体和帖子的状态

`media.sync_status` 和 `post.sync_status` 是汇总出来的摘要，给列表筛选和角标用，不另存失败的详情：

- 有来源在 `IN_PROGRESS` ⇒ `IN_PROGRESS`；否则有来源在 `PENDING` ⇒ `PENDING`。还在同步的来源优先于失败的来源，和现在"还有能成功的来源就继续重试"一致。
- 没有同步中的来源，但有 `FAILED` ⇒ `FAILED`。
- 其余 ⇒ `COMPLETED`。

每个写来源行的地方（导入、下载、编辑器、重试）都在同一个事务里先锁帖子，再刷新媒体和帖子的摘要，沿用现在 `lockPosts` 加 `refreshPostSyncStatus` 的顺序。

导入时就声明了 `kind`，并且校验了组合（第 6 节），下载时又逐个核对，所以全部来源 `COMPLETED` 时组合一定成立。下载完成后的组合校验（`getMediaCompletionError`）因此删掉。摘要不存失败详情，`media.last_error` 和由它拼出来的 `post.last_error` 也都删掉。失败列表改成从来源行查。

## 5. 错误分类

在 download 这一层统一把异常归类成 `error_kind`，写法参照 `features/ai/errors.ts`：

| `error_kind` | 来源 | 处理 | 用户能做什么 |
|---|---|---|---|
| `NETWORK` | 超时、连接断开、5xx、429 | 退避重试，次数用完后记为 `FAILED` | 重试 |
| `SOURCE_UNAVAILABLE` | 400、404、410；403 在同一次运行里隔几秒（等待要响应 `ctx.signal`）重试 1 次，还是 403 才算 | 直接 `FAILED` | 到采集端重新分享这个帖子，或者在编辑器里修 |
| `KIND_MISMATCH` | 探测出的内容和声明的 `kind` 不符（第 7 节） | 直接 `FAILED`，文件不入库 | 在编辑器里修；采集端修好后重新分享 |
| `UNREADABLE` | 探测失败、格式不支持、字幕转换失败 | 直接 `FAILED` | 在编辑器里修 |
| `INTERNAL` | 其他错误：存储失败、程序 bug、运行超时 | 退避重试，次数用完后记为 `FAILED` | 重试；反复出现说明是 bug |

- 403 的取舍：[job_queue.zh-Hans.md](./job_queue.zh-Hans.md) 6.1 节记过"CDN 也会临时返回 403"，所以不直接拒绝，先短重试一次。过滤偶发的抖动只多花几秒；真的签名过期也不用白等 5 轮退避。
- 判断不准的错误一律归为 `NETWORK` 或 `INTERNAL`，也就是可以重试的那一类，沿用现有"只有确定是输入的问题才拒绝"的规则。
- `last_error` 放技术细节，比如状态码和主机名。界面一律按 `error_kind` 显示，不解析 `last_error` 的文本。

## 6. 导入协议

这是破坏性的变更，采集端（stationary-script）要同时修改。

```text
originals[]   至少 1 个  { url, source_key, kind, language?, label?, is_default? }
kind          VIDEO | AUDIO | IMAGE | PDF，必填，和 OriginalKind 一致
```

- **入口按声明的 `kind` 校验组合。** 规则就是 `compositionError`，换成用声明的 `kind` 来算，取代现在只检查数量的 `originalCountError`。不通过就返回 400，并指出是哪个帖子、哪个媒体、哪条规则。
- **`kind` 怎么填。** VIDEO 里含视频流的那个原件填 `VIDEO`，单独的音轨填 `AUDIO`。LIVE_PHOTO 填一个 `IMAGE` 加一个 `VIDEO`。采集端拿不准某个流有没有视频，就不要推送它。
- **采集端的重试。** 采集端是手动触发的：用户把帖子链接分享给采集端，采集端抓取后推送过来。它自带自动重试，但只能对网络错误和 5xx 重试；400 是确定的输入问题，重试只会一直失败，应该直接提示用户。
- **`source_key` 的规则不变。** 采集端修好内容后不需要换键：签名 URL 每次都不一样，新的 URL 会让失败自然作废（第 4.2 节）。
- **原件按键和 `kind` 一起匹配。** 已下载的文件只核对过当时声明的 `kind`，所以同一个键换了 `kind`，就当作新的原件：旧的连同从它提取的数据一起删掉，新的重新下载、重新核对。
- **字幕和封面不需要声明 `kind`**，它们的种类本来就是固定的。

## 7. 下载时的准入校验

下载并探测原件之后、写入文件列之前，用探测结果算出 `kindOfProbe`，必须和声明的 `kind` 一致：

- 一致：照常写入 `av_file`、`av_stream`、内嵌的字幕、歌词和封面，并更新媒体的摘要，原件记为 `COMPLETED`。
- 不一致：软删除刚上传的 `File`，其他什么都不写，原件记为 `FAILED`、`KIND_MISMATCH`，`last_error` 写明声明的是什么、探测出的是什么，比如"声明为 VIDEO，探测结果只有音频"。

这样 1 节里的两种坏内容都会停在**原件**这一级，并且有准确的原因，不会再变成媒体级的组合错误。字幕转换失败、封面不是可以读的图片，都记为 `UNREADABLE`。

## 8. 所有权：同步不撤销用户的修改

### 8.1 被排除的来源键

`media` 上新增一列 `excluded_source_keys text[]`，元素带类别前缀，比如 `original:video`、`caption:zh-CN`、`cover:cover`。同步时跳过这些键。

- 用户**删除**一个导入的来源：删掉这一行，并把它的键加入排除列表。
- 用户**替换**一个导入的来源：排除旧键，再插入一条普通的上传行（没有 `source_url` 和 `source_key`），并继承旧行的 `language`、`label`、`is_default`。
- 这样不用放宽 `*_source_pair` 约束，也不用在来源表里留墓碑行，免得播放和组合查询都要绕开它们。
- 以后如果要做"恢复为导入的版本"，就是把这个键移出排除列表，再删掉用户上传的那一行。这次不做。

### 8.2 用户改过的字段

`media` 和 `post` 上各加一列 `user_edited_fields text[]`。用户通过 `update-info` 或改类型改过的字段记进这一列，再次导入就不再覆盖这些字段：

- 媒体：`type`、`title`、`description`、`published_time`。
- 帖子：`title`、`description`、`published_time`。
- 标签已经按来源区分（`TagSource.SCRAPER`），不放进这一列。

### 8.3 同步按"生效的类型"取舍来源

`syncImportedSources` 传入的是**生效的** `media.type`：用户改过类型就用用户的，否则用这次导入的。现在传的是导入数据里的 `type`（`persistence.ts:227`），要改掉。

- **原件：** 一个导入原件的声明 `kind`，必须在生效的类型里还有空位，才会同步进来。被用户上传的原件占住的位置，不再插入导入的原件。
  - 例：用户替换了主视频之后，采集端把键从 `video_1080` 换成 `video_4k`，新来的 `VIDEO` 原件会被跳过。
  - 例：用户把 LIVE_PHOTO 改成 IMAGE 之后，导入的 `VIDEO` 原件会被跳过。
  - VIDEO 的 `AUDIO` 原件没有数量限制，照常同步。
- **封面：** 已经有用户上传的封面（没有 `source_key`）时，跳过导入的封面，不覆盖也不删除。生效的类型不能有封面时，同样跳过。
- **用户删除的媒体继续保持删除**，和现在一样。

## 9. 用户修复和界面

### 9.1 编辑器里的修复操作

都在媒体编辑器（`MediaEditor.vue`）里完成。每个操作都同步探测、校验组合，不通过就返回 400，什么都不写：

| 操作 | 说明 |
|---|---|
| 替换来源 | 上传文件替换原件、字幕或封面（第 8.1 节）。原件替换已有（`addOriginal` 的 `replaces`），要加上排除旧键 |
| 删除来源 | 删除原件、字幕或封面，并排除它的键。原件删除仍然要求组合成立 |
| 改类型 | **新增。** 一次请求带上新的类型和要删除的原件，作为整体校验，比如 LIVE_PHOTO → IMAGE，同时删掉坏的"视频"。类型记入 `user_edited_fields` |
| 重试 | 只对 `NETWORK`、`INTERNAL` 显示，作用于单个来源 |
| 删除媒体 | 已有 |

不支持手动填写来源 URL：签名地址很快就会过期，上传已经能解决这类问题。

### 9.2 四个视图

失败的事实只存在来源行上，各个视图从不同的角度显示它：

| 视图 | 读什么 | 回答什么问题 | 能做什么 |
|---|---|---|---|
| 媒体编辑器 | 每个来源的 `status`、`error_kind`、`last_error` | 具体是哪个文件出了问题，为什么 | 第 9.1 节的全部操作 |
| 媒体卡片、批量操作栏 | 媒体的摘要状态，加上最主要的那个 `error_kind` | 这个媒体有没有问题 | 显示一句原因，点开进编辑器；只有可以重试的失败才显示"重试" |
| 帖子详情 | 帖子的摘要状态，以及里面每个媒体的状态 | 这个帖子完整吗 | 有 `SOURCE_UNAVAILABLE` 时显示平台链接，提示"在采集端重新分享这个帖子"；其他问题链接到对应的媒体 |
| 任务页（`/jobs`） | download 流水线查来源行上当前的失败，按 `error_kind` 分组 | 整个库还有多少下载问题，主要是哪一类 | 按组处理：`NETWORK`、`INTERNAL` 可以批量重试；`SOURCE_UNAVAILABLE` 列出帖子和平台链接；`KIND_MISMATCH`、`UNREADABLE` 链接到编辑器 |

文案按 `error_kind` 写：

| `error_kind` | 给用户看的原因 |
|---|---|
| `NETWORK` | 网络问题，下载没有完成 |
| `SOURCE_UNAVAILABLE` | 平台的链接已经失效，需要重新分享这个帖子 |
| `KIND_MISMATCH` | 文件和声明的类型不符（显示声明的类型和实际的内容） |
| `UNREADABLE` | 文件无法读取，或者格式不支持 |
| `INTERNAL` | 服务器出错 |

- **重试只做一件事：** 把可以重试的失败改回 `PENDING` 再入队。`retry-sync.ts` 和 `retryFailures` 都只处理 `NETWORK`、`INTERNAL`。
- **"同步中"和"重试中"：** 来源是 `PENDING` 并且带着错误时，显示"重试中"和原因，不放操作按钮。

## 10. avatar

avatar 也是一次性落地，以后按同样的规则改：

- 用稳定的键表示"是哪个头像"，不用 URL 本身。现在每次导入都会写入新的 `avatar_source_url`（`persistence.ts:56`），如果头像 URL 带签名，每次同步都会重新下载一遍。键可以由采集端提供，也可以由服务端从 URL 规范化出来，到时候再定。
- 失败绑定到当时的 URL，使用同一套 `error_kind`。

这次不改 avatar 的代码：它不在第 1 节的失败里，而且需要采集端配合。

- **给已有的导入原件补 `kind`：**
