# 系统架构设计取舍与 Trade-offs

本篇文档主要详述 Stationary 项目在开发过程中的技术决策、系统架构折中方案以及多媒体处理策略的选取考量。

---

## 1. 多轨道媒体表达模型 (Track 与 File 的拆分设计)

### 背景与决策
多媒体资源在物理实体构成上常常极其复杂。例如，音视频轨分离的媒体资源（如 fMP4 分片）；Live Photo（实况照片）由一张静态封面图和一段短视频共同组成；单个视频资源在播放时除了主视频/音轨外，往往还需要视频封面、预览图以及字幕文件。

为此，Stationary 采用了 **“多轨道模式”**：
- `Media` 表作为逻辑媒体资产的统一容器。
- `Track` 表（轨道变体）记录当前媒体下各个关联组件和角色的详细配置（通过 `type` 指定 `IMAGE`, `VIDEO`, `AUDIO`, `SUBTITLE`，通过 `purpose` 指定 `CONTENT`, `COVER`, `THUMBNAIL`, `PREVIEW` 等）。
- `File` 表指向存储于 S3 上的具体物理文件，以 UUID 唯一标识。

### 核心考量 (Rationales)
- **极高扩展性**：未来当需要为视频增设多路多国语言字幕、多档低码率预览流或 AI 标注生成的缩略图时，只需在 `Track` 表新增记录并绑定对应的 `File`，完全不需要对 `Media` 表结构执行物理 DDL 迁移。
- **细粒度更新与去重**：当某路辅助轨道（如字幕或防盗链 Token 变化的音轨）需要更新时，仅需重新同步和替换单条 `Track` 及物理文件，避免了对主要高清视频资产的重复下载和存储浪费。

## 2. 播放：先直接播放原件，需要时才用清单和即时打包

### 背景与决策
一个视频可能是一个普通 MP4，可能是内嵌多条音轨的 MP4，也可能是视频加上外接的音频文件（MP4、M4A、fMP4）和字幕。Stationary 不存储转码或重封装的副本：直接播放原件能满足需要时就直接播放，否则才用请求时生成的 HLS 或 DASH 清单。细节见 [media_refactor.zh-Hans.md](./media_refactor.zh-Hans.md) 第 8 节。

- **服务端给地址，客户端选择。** `direct_url` 一直都有。有多个原件、多条音轨或有字幕，并且视频流能进清单时，再给 `hls_url` 和 `dash_url`。
- **清单引用什么。** 带 `sidx` 的单流 fMP4 按字节范围直接从 CDN 引用。普通 MP4、MOV、M4A 即时打包：服务端用 Range 请求读出 `moov`，自己写 `moof`，把样本字节从 S3 读出来，按 fMP4 分片转发。其他格式（MP3、MKV、不带 `sidx` 的 fMP4）不进清单。有没有 `sidx`、是不是分片文件，在探测时用 Range 请求读出，存在 `av_file`；逐个分片的索引缓存在 Redis。
- **网页播放器。** 用原件还是清单由选中的音轨决定。原件能给的音轨用普通 `<video>` 直接播放：Safari 能用 `audioTracks` 原地切换原件里的音轨，其他浏览器只播文件里的第一条。其他音轨用清单播放（hls.js；dash.js 是设置里的高级选项）。两个方向都会切换，从原来的位置继续，新来源开始播放前画面、时间和播放状态都停在切换那一刻。
- **Flutter 和外部播放器。** Flutter 只有一个原件时直接播放，在播放器里切换内嵌音轨；有外接音轨时用 HLS（AVPlayer 不支持 DASH）。外部播放器拿原件地址；有外接音轨或字幕时拿清单地址。

### 核心考量 (Rationales)
- **大部分播放不经过服务端。** 原件用 HTTP Range 请求直接从 CDN 读。即时打包的分片要经过服务端转发，占用服务端带宽，只有需要清单的媒体才付出这个代价。
- **不存副本。** 原件只增不改，没有派生的音视频文件，就不存在同步和迁移的问题。打包索引随时可以重算。
- **交错存放的原件只需几次读取。** ffmpeg 逐个样本交错存放音视频，一个 6 秒的分片散成约 180 段。间隔不超过 32 KiB 的段合并成每次最多 1 MiB 的读取，并向前并发，一个分片的耗时从约 6 秒降到 0.2 到 0.4 秒。
- **支持有边界。** 边界外的格式在播放器里标为不可用并说明原因，不做无限兜底（media_refactor 第 16 节）。转码是远期选项。

## 3. 媒体主体向量化 (不执行 Post 维度直接向量化)

### 背景与决策
我们在 `Media` 维度上（`entity_type: EntityType.MEDIA`）为搜索引擎计算并持久化向量嵌入，而不是在 `Post` 维度，尽管 `Post` 才是包含媒体的逻辑实体主体。

### 核心考量 (Rationales)
- **检索粒度精准度**：Stationary 最终呈现给用户的“资产视图 (All Pins)”是纯图片/视频级别的 Masonry 布局。当搜索触发时，结果必须对应到可以直接预览或下载的具体物理图片或视频。
- **上下文信息注入 (Context Injection)**：在 AI 富化执行 `enrichMediaItem` 时，系统在生成 Media 描述时会自动注入父级 `Post` 的标题与描述。因此，在对 `Media` 的向量表示进行相似度查询时，隐式地包含了对父级帖子上下文的模糊检索能力。
- **去重与空间开销**：如果针对 `Post` 额外做一套向量计算，在实际资产列表里没有物理媒体承载的情况下会产生数据冗余，徒增计算费用和向量库存储开销。

## 4. 封面与缩略图离线生成策略 (Cover & Thumbnail Generation)

### 背景与决策
为适配不同的展示布局（看板卡片封面、网格缩略图滚动、大图查看与视频播放），系统建立了轻量化的 **封面与缩略图生成架构**：

- **Tier 1 (Original Master)**：原始图像或视频文件，用于高保真保存与下载。
- **Tier 2 (Cover / Thumbnail)**：系统在本地/服务端自动截取视频关键帧或缩放图像生成 AVIF/WebP 格式封面（如 400px 缩略图），用于列表防卡顿流式滚动。

### 核心考量 (Rationales)
* **本地异步生成**：由后台任务队列的 `cover` 流水线异步解析源文件并提取封面帧，写入 S3 与对应的 `Track` / `File` 记录。
* **低算力开销**：视频播放直接由前端播放器通过 HTTP Range 范围请求播放 Tier 1 原始文件，避免了高昂的视频全量重新编码/压制成本。
